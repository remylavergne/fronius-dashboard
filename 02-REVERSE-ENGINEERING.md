# Reverse engineering of the Fronius Web client

## Webpack module mapping
| Module | Role and elements found |
|---|---|
| `mgOI` | Login component, injection of `_commands` via `p = n("i3oe")`; setup access keys distinct from Technician. |
| `i3oe` | Command service: `Login`, `Logout`, `SetPassword`, `ActivatePasswords`, other commands. |
| `JWhm` | Base HTTP class: `callGet$`, `callPost$`, `callGetWithoutCatch$`, `callPostWithoutCatch$`, `_getUserAndPass`. |
| `CNEH` | Local storage of the `AuthHash` credentials. |
| `LsM5` | Login DAO / update of the NgRx store. |
| `nuFz` | `[Login] login` action and role logic in the store. |
| `ytu1` | Generation of the HTTP Digest headers. |

## Authentication
- [SOURCE-JS] `GET /commands/Login?user=<username>`; the `i3oe` service passes `{user: username, password, type: passwordUser}`.
- [SOURCE-JS] `JWhm._getUserAndPass`: `passwordUser` returns `username:password`; `fallback` retrieves the credentials from `_requestGroup`.
- [SOURCE-JS] `JWhm.callGet$` and `callPost$` retry **once** on HTTP 401 after reading `x-www-authenticate` and refreshing the nonce. `Authorization` header computed by `ytu1.DigestHeader`.
- [OBSERVED-CONVERSATION] Realm `Webinterface area`, MD5 algorithm, particular Digest mechanism with `X-WWW-Authenticate`; a Python urllib client with specific support has already worked for Customer GETs.
- [SOURCE-JS] `CNEH` writes `localStorage.setItem("AuthHash", username + ";" + password)`: **credentials in clear text**; never reproduce this storage in the new frontend.
- [SOURCE-JS] Angular defines cumulative roles: `user` (`RoleEverybody`), `customer` (+`RoleCustomer`), `technician` (+`RoleTechnician`), `support` (+`RoleSupport`), `profi` (+`SetupAccessRole01`), `utility` (+`SetupAccessRole02`). These names are those of the client, not proof of effective server permission.
- [SOURCE-JS] Keys hardcoded in the setup component `77634` and `86536`; they concern Profi/Utility-type unlocks, **not Technician passwords**.

## Derivation of the new passwords
- [SOURCE-JS] `createNode(user, password, includeSalt)`: `hashedPassword = MD5("user:Webinterface area:password")`; for a user other than `user` and a non-empty password, PBKDF2 with **100,000 iterations**, **64-byte** output, **4-byte** salt generated by `Math.random()` then represented in hexadecimal.
- [SOURCE-JS] `pbkdf2_salt` is only set if `includeSalt` is true; `pbkdf2` is computed when the conditions are met.
- [SOURCE-JS] Do not infer the exact PBKDF2 PRF from this single excerpt: follow the crypto import for confirmation.

## Recovery
- [SOURCE-JS] `GET /commands/PasswordRecovery?user=<user>` obtains a challenge / `remainingSignatureChecks`.
- [SOURCE-JS] `recoverPassword()` sends a POST request with `new` (HA1 MD5), `pbkdf2_salt`, `signature`, and the field `pbkdf2_technician` / `_support` / `_customer` / `_user` depending on the account.
- [SOURCE-JS] The browser **does not compute the signature**: it is entered in the form then transmitted. Verification on the firmware side, possible failure `ERROR_VERIFY_SIGNATURE`.
- [OBSERVED-CONVERSATION] Do not try random signatures; number of attempts limited.

## Maintenance
- [SOURCE-JS] `SupportAccount` exposes activation/deactivation and session termination with `resetPassword: true`: do not call without an explicit goal and verification of rights.
- [SOURCE-JS] `CreateSDPFile` → status → `GetSDPFile` to download `sdp.cry`. Internal format unknown, do not assume it contains exploitable secrets.
- [SOURCE-JS] `ServiceFile` refers to `service.data`.
- [OBSERVED-CONVERSATION] Angular routes with guard `oi.a`; **its implementation and the component checks remain to be audited**. Do not present a matrix of page permissions as validated.

## Result on Technician
No password, signature secret or autonomous recovery means confirmed. Legitimate leads: old browsers/profiles, password managers, installer documentation, official procedure. Do not bypass the protections or modify the electrical network settings.
